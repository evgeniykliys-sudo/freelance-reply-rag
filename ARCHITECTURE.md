# Архитектура: freelance-reply-rag

## Цель (1 предложение)
Telegram-бот: присылаешь текст заказа — бот ищет подходящую услугу/бриф/портфолио
в базе (FREELANCE.md) и составляет черновик отклика строго на найденном, либо
честно говорит, что заказ не подходит.

```
Текст заказа
     │
     ▼
embedder.encode()  (paraphrase-multilingual-MiniLM-L12-v2)
     │
     ▼
ChromaDB.query()  →  top-10 чанков + L2-дистанция
     │
     ▼
фильтр по MAX_RELEVANT_DISTANCE  →  если пусто — "вне профиля", без черновика
     │
     ▼
Claude (grounded-промпт: только то, что в чанках; явный отказ, если в
чанках есть стоп-лист; формат ответа — приветствие+proof+вопрос)
     │
     ▼
Черновик + пометка для Евгения (какая услуга/цена использована)
```

## Модули
| Модуль | Файл | Описание |
|--------|------|----------|
| Индексация | ingest.py | Парсит FREELANCE.md под его структуру (не общий чанкинг): строки таблицы услуг и портфолио — по одной как чанк, бриф-шаблоны и шаблоны откликов — каждый целиком |
| Поиск + генерация | rag.py | `search()` — топ-k чанков с дистанцией, `draft_reply()` — grounded-генерация черновика через Claude |
| Telegram-обёртка | bot.py | Принимает текст заказа, вызывает draft_reply(), отвечает |

## Откуда данные и почему не дублируются
`ingest.py` читает `C:\Projects\_docs\FREELANCE.md` напрямую (путь захардкожен,
проект для личного использования, не для чужого окружения). Чанки не копируются
в отдельные markdown-файлы — источник один, обновление цены/услуги = перезапуск
`ingest.py`, а не ручная синхронизация двух копий.

## Что чанкуется и как
- **Услуги** (строки таблицы) → `Услуга: X\nЦена: Y\nВходит: Z\nНЕ входит: W`
- **Бриф-шаблоны** (`## Бриф-шаблон: X`) → весь раздел целиком (вопросы + что получает заказчик)
- **Портфолио** (строки таблицы) → `Проект: X\nСтек: Y\nСсылка: Z`
- **Шаблоны откликов** → каждый `**Заголовок:** > текст` отдельным чанком
- **Навыки** → один чанк
- Сознательно НЕ индексируются: "Платформы" и "Стратегия" — внутренние заметки
  (демпинг, какие Telegram-каналы живые), не то, что должно попасть в текст
  клиенту даже косвенно через retrieval.

## Эмбеддинги: почему не та же модель, что в rag-faq-bot
rag-faq-bot использует `all-MiniLM-L6-v2` (в основном англоязычная модель) — для
документации на английском ок, для русского хуже. Здесь и база, и входящие заказы
на русском, поэтому `paraphrase-multilingual-MiniLM-L12-v2`.

## Дистанция и порог отсечения
ChromaDB по умолчанию — squared L2, **не** косинус 0-2 (первая калибровка была
на неверной шкале — см. git-историю). Откалибровано на реальных примерах
(`scripts/calibrate.py`): совпадения по профилю — дистанция ~9-14, заказы вне
профиля (дизайн, не-IT) — от ~19.5. `MAX_RELEVANT_DISTANCE = 16.0` — запас
между этими кластерами. Это грубый предфильтр (чтобы совсем не по теме не
доходило до LLM); тонкую семантическую оценку (например "это наём, а не разовая
услуга" — хотя чанки по дистанции прошли фильтр) всё равно делает сама модель
по инструкции в промпте, а не код.

## Анти-галлюцинация
Промпт `rag.py::SYSTEM_PROMPT` явно запрещает использовать цены/услуги, которых
нет в переданных чанках, явно требует честно сказать "не подходит под профиль"
вместо притягивания услуги, и явно требует отказа (не продающего текста), если
в чанках есть стоп-лист на конкретный тип работ (обход защиты и т.п. — уже
есть в FREELANCE.md как "НЕ входит"/"НЕ беру" у браузерной автоматизации).
Проверено на 5 типах заказов в `scripts/test_draft.py`, включая погранично
корректную реакцию на вакансию (не разовая услуга — не пишет черновик, а
объясняет разницу и предлагает альтернативу).
